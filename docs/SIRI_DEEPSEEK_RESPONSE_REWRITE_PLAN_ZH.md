# AIES：Siri 原生界面 DeepSeek 回答替换实施计划（v1.0）

> **计划进度提示**：本计划 P0 已完成；P1–P3 有 [v0.6 Clean Beta 候选实现](https://github.com/Nimenta727/Apple-Intelligence-Exchange-Secure/tree/siri-deepseek-v0.6-clean)，但真实 Siri UI、真实 DeepSeek Key 接入、P4 来源保证、P5 后续隐私结构优化及 P6 发布审查尚未完成。用户选择直接集成、随后集中真机测试，不再要求逐项运行 40 等 Safari 旧探针。最新状态参见 [v0.6 进度](https://github.com/Nimenta727/Apple-Intelligence-Exchange-Secure/blob/siri-deepseek-v0.6-clean/docs/CURRENT_STATUS_ZH.md)。


> 决策日期：2026-11-18。状态：**已批准的工程目标与执行计划；尚未完成响应替换实现或真机验收**。本文是新路线的执行基准，取代旧路线中的“必须阻断千问原始出站”这一产品约束；旧研究文档保留为历史证据，不代表新版本现已可用。

## 0. 一句话目标

**保留 Siri 原生唤醒与结果界面；用户指定的 Siri 文本问答，最终呈现的 AI 回答只能来自用户授权的 DeepSeek API，不能来自千问。**

用户已明确接受：原始 Siri 请求可能按原有路径发送给千问，并允许千问作为协议骨架来源。这里不承诺隐私隔离或零千问出站；也不声称千问不会处理问题。**允许请求经过千问，不等于允许最终答案回退千问。**

### 成功条件与边界

- Siri 原生界面显示 DeepSeek 的回答；不得通过快捷指令弹窗、独立 App、网页或纯朗读来冒充“原生 Siri”。
- 只做目标接口的 Siri **文本问答**；写作工具、视觉智能、多媒体、复杂多轮、模型切换、管理后台等均不属于 MVP。
- 从用户所见角度，DeepSeek 回答是唯一可接受的 AI 答案来源。来源失败、无法确认替换、脚本没有运行、系统自动回退到千问时，**不能声称满足目标**。
- 安全策略是“可证明的答案来源 + 最小权限 + 尽可能失败关闭”，不是“零数据送千问”。在无法控制系统层回退时，必须明示能力边界并将版本标为实验性。
- 本文不授权立即启用真实域名转发。旧 00 REJECT 在当前实验配置继续生效；要测试允许千问连接的新模式，必须**使用单独的可回滚实验配置**、得到明确的真机测试授权并先完成离线检查，不得悄悄修改现行 00 模块。

## 1. 当前代码与已完成实验（事实）

仓库 main 为 v0.4.0-lab。现有：
- src/request.js：对固定目标 URL/POST/JSON/文本场景做解析与长度限制，**可复用，但需按真实响应替换链路复审**。
- src/deepseek.js：封装固定 Chat Completions Endpoint、授权头、HTTP 返回解析；**可复用，但模型参数与 Shadowrocket API 行为需复核**。
- src/sse.js：离线“从零生成”候选 SSE；**不是**基于真实千问 SSE 进行安全改写的现成实现。
- src/core.js、src/entry.js：目前为 http-request 的本地伪造响应流程，遇到 providerEnabled:false 返回拒绝；**不能直接启用即视为新路线完成**。
- tools/build.js 与 scripts/sairs_router.js：确定性构建、CI 的生成文件一致性检查。新结构仍需保留确定性构建和语法测试。
- 00/10/20/21/30/31：旧阻断或虚构域名研究模块。不得复用 10 为新路线成品，30/31 仅研究用途。
- 用户在 Shadowrocket 2.2.93 (3488) 的虚构域名实验：30 的 ok/deny 返回成功；throw/nodone 显示连接错误；31 同域 REJECT 命中，无法取得本地 Mock。该结果**不验证**真实 Siri 的 http-response 改写、会话匹配或 DeepSeek 真实调用。
- PR #7 是 choice_index 校验研究；PR #8 是旧接管故障对照；两者非新 MVP 的交付前提，暂不自动合并。

本次计划的关键技术假设（**都需要证据**）：
1. Siri 目标文本请求可以被 Shadowrocket http-request 读取，且响应阶段 http-response 可得到足够的 SSE 内容并安全替换。
2. 请求和响应可基于可靠的关联标识衔接；不同脚本实例之间的持久/共享状态、生命周期、清理机制必须真机核验。
3. SSE 可能是流式传输；Shadowrocket 的响应体捕获、缓冲、大小上限、超时、脚本重入，以及 Siri 接受完整替换的时序必须实测。**不能默认仅靠替换字符串即可生效。**
4. DeepSeek 调用完成时机必须早于 Siri 最终消费响应；若无法实现，尽早判定架构不成立，不能通过静默回退千问掩盖问题。

外部参考（需在开发时复核版本）：DeepSeek 官方 Chat Completions 文档 https://api-docs.deepseek.com/api/create-chat-completion/ 和更新日志 https://api-docs.deepseek.com/zh-cn/updates/；Shadowrocket 的具体引擎行为优先以当前设备真实日志为准，不将第三方文档当作已验证行为。

## 2. 推荐架构：请求捕获 + DeepSeek + 响应重写

目标流：

1. Siri 发出符合白名单的文本请求（固定 HTTPS host/path + POST + 受限 JSON）。
2. **request 阶段**仅提取规范化问题、受限场景与关联上下文；允许原始请求继续按配置转发给千问。记录短期内部 token，不在诊断日志记录原文。
3. **DeepSeek 阶段**以固定 Endpoint / model、最小请求体和设备本地密钥调用；完成后产出“待替换回答”状态。启动时机由 P1 真机能力测试决定：请求阶段启动并保存结果 / 响应阶段等待 / 等效的单一会话协调机制。未经实测**不要将跨阶段共享变量写成可靠方案**。
4. **response 阶段**读取千问 SSE，仅把它当作结构参考。先识别事件、目标字段、编码、边界、关联 ID，之后将所有 AI 回答载体（delta、最终值、嵌套 choice/output、可能的补充文案）一致替换为已确认的 DeepSeek 内容；保持必要 ID、顺序、状态和消息完整性。
5. **安全门**：只有来源校验通过 + 全量输出字段审计通过 + 结构校验通过，才返回标记为 DeepSeek 来源的响应。任何不一致必须触发失败路径；既不能把千问正文返回，也不能保留“千问答案的局部片段”。
6. **Siri 验收**：以原生 Siri UI 显示和重复真机结果为最终依据。脚本记录的 REWRITE_ATTEMPTED 不等于客户端显示成功。

特别说明：响应体若只能分片处理、不能安全获得或无法全量替换，则停止该实现思路，评估响应流处理能力或更可靠的客户端接管方式；不在未证实的前提下发布。

## 3. 分阶段交付与验收门槛

### P0：冻结需求、建立隔离分支与风险台账

交付物：siri-deepseek-response-rewrite 开发分支；本文；旧路径和新路径的配置对比；新增诊断与回滚方案。

动作：
- 保留 main 的旧实验默认行为，新增独立实验模块与脚本，不直接改写 00/10。
- 列出必须支持/明确不支持的 Siri 场景，并确认用户同意原始文本可能送至千问及 DeepSeek。
- 将“来源不明不能显示千问回答”写成自动测试和发布阻断规则。
- 实现版本锁定、标记开关和一键撤销说明。

验收：需求、信任边界、测试范围、风险接受与回滚条件均可从 docs 查到；无 Key、敏感请求或证书进入 Git。

### P1：最小协议与宿主能力探针（第一个真正的技术门槛）

交付物：仅固定假回答、无真实 DeepSeek Key 的 request/response 双阶段探针；最小 SSE fixture；对应离线测试。

分为两条：
- P1-A：虚构测试域名上验证 http-response 是否能替换 JSON/SSE；分别测试完整响应、分块、压缩编码、超时与重复请求。
- P1-B：在用户明确授权的隔离实验配置中，用**非私人、固定测试问题**验证真实 Siri 原生显示固定标记（例如 AIES_TEST_FROM_REWRITE_001），并核实 request/response 关联、Siri 界面显示和是否出现多条回答。

关键实验变量：response 是否能取到完整 body、req↔res 可关联的稳定 token、原响应是否分块、Content-Length/Content-Encoding/ETag、脚本时限和系统重试。

验收：Siri 原生界面明确展示固定替换文本，且识别到的全部 AI 文本字段一致；在并发、失配、失败路径不显示千问正文。若达不到，**暂停后续 DeepSeek API 逻辑**，仅解决此门槛或作出不可行结论。

### P2：真实 DeepSeek API 适配

交付物：独立可测试的 API Adapter；安全初始化/撤销 Key 方案；完整模拟 HTTP 测试。

动作：
- 从现有 src/deepseek.js 提取 adapter，官方文档核对 model、Endpoint、认证格式、返回 JSON 以及当前模型可用性；**不硬编码长期假设**。
- 默认 1 次请求、无自动隐式重试，设定成本/输出长度/总超时上限；明确区分 401/403/429/5xx/网络失败、空结果、截断和内容类型错误。
- 以脱敏测试 prompt 进行**用户授权的真实 API**小额联调；不发送真实隐私内容到公开调试设施。
- 回答保留原始 DeepSeek 文本，不使用千问输出补全或重新生成 AI 答案；必要的编码/结构包装不改变来源。

验收：独立 API 调用成功，Token/Key 不泄露，错误状态明确，输出可核对来源；无需依赖 Siri 网络链路完成 API 单元测试。

### P3：请求—模型—响应闭环集成

交付物：最小可安装实验模块、两个入口脚本或由能力验证决定的等价入口、清晰的会话状态机、最小使用说明。

建议状态机：CAPTURED → MODEL_PENDING → MODEL_OK → REWRITE_VERIFIED → DONE；失败为 FAILED/CANCELLED/EXPIRED。

关键实现：
- 关联 token 必须防碰撞、限定 TTL，且不得使用用户问题或 API Key 作为 key。
- 请求竞争/并发/重复回调/系统重试须去重；异步结果迟到应忽略并清理。
- 在返回任何 AI 内容前，需将候选 SSE 中所有可能包含千问回答的字段做**允许名单型替换审计**。遇未知事件、新字段或原文残留，一律不得以成功结果放行。
- 输出阶段同时验证 session/choice/item/content 的 ID 与所有 delta/done/final 的内容一致；不要求沿用旧从零生成 SSE 的全部逻辑。
- MIME、长度、压缩和 SSE 完结标志处理遵循真实客户端能力。必要时先发出固定、非千问的安全错误；若宿主不能保证禁止原始响应回退，则该路径判定为不满足产品目标。

验收：连续多次原生 Siri 提问显示 DeepSeek 回答；不同问题、连续提问和同时触发时无串话；无千问回答片段残留。

### P4：来源保证与失效安全（发布硬门槛）

交付物：失败注入测试报告、真机验证矩阵、发布/回退判断。

必须覆盖：
- DeepSeek 网络断开、HTTP 401/429/5xx、API Key 无效、模型返回空/畸形内容、超时；
- 千问 SSE 格式变化、stream 分块/压缩、超大 body、字段缺失、未知 event；
- 请求/响应关联丢失、双请求交错、脚本未触发、脚本异常、设备锁屏、Shadowrocket 未运行、VPN 切换；
- 漏出原始千问回答、只替换一部分、重复 delta、混合来自两个模型的文本、Siri 自身展示系统级缓存/回退。

**发布门槛：**
- DeepSeek 成功：原生 Siri UI 实际显示 DeepSeek 答案；来源测试采用差异显著的固定回答与可审计的模拟回复，不能仅凭 API 请求已发送判断。
- DeepSeek 失败：不得呈现千问生成的 AI 回答。若无法在所有相关故障路径控制该行为，则只能标示“尽力替换实验”，**不能承诺‘答案一定来自 DeepSeek’**，并应停止宣称产品完成。
- 不记录/上传原文、Key、Authorization、Cookie、证书私钥、完整 SSE 或可识别内容。
- 所有必需 CI 检查、真机最小矩阵和回滚复测通过；版本与设备前提明确。

### P5：代码优化与结构简化（功能通过后单独做）

**明确是正式开发阶段，不是以后有空才做。** 先冻结 P1–P4 的通过用例与安全特性，随后在独立重构提交中优化，确保行为不回退。

拟定的最终核心结构（依据 P1 实验确定，目录只是建议）：

    src/config.js           # 安全配置与白名单
    src/request.js          # Siri 文本解析及输入限制
    src/deepseek.js         # 唯一模型适配与响应合法性
    src/session.js          # 短期关联、TTL、并发和去重（若宿主需要）
    src/rewrite.js          # SSE 安全解析、答案替换和完整性审计
    src/entry-request.js    # Shadowrocket request 薄适配
    src/entry-response.js   # Shadowrocket response 薄适配
    tools/build.js          # 确定性构建，生成一或两个部署脚本
    tests/                  # 含固定 fixture、错误注入与宿主模拟
    shadowrocket/           # 仅一个明确命名的 MVP 实验模块

具体约束：
- 不重复实现 SSE 解析与序列化；淘汰不再用于新路线的“从零构造 SSE”部署路径，保留在 history/ 或 git 历史中。
- request / provider / rewrite / session / runtime bridge 各自职责单一，依赖方向清晰；将宿主特定 API 集中在薄入口层，核心函数纯净、可单元测试。
- 消除旧 00/10/20/21/30/31 的产品入口混淆，研究模块移至 history/ 或标注 LAB_ONLY；新模块只对一种明确运行模式负责。
- 合并重复配置与校验，移除死代码和未用分支；避免依靠全局变量、持久化原始用户问题、同步等待、散落的魔法值。
- 不做无收益的“过度抽象”。核心逻辑优先小文件、显式状态、可追踪错误码和注入式宿主接口。
- 性能与资源：限制 request/response body、事件数、内存、并发数、TTL，防止长时缓存、重复 DeepSeek 费用与响应阻塞。
- 优化前后必须使用**同一套** fixture、失败测试和真机验收矩阵；任何输出来源保证退化均回滚。
- 升级说明、配置迁移、卸载/停用步骤和已知限制必须同步更新 README 和 docs；检查许可证与上游归属。

P5 验收：代码职责清楚、配置入口唯一、部署脚本可重复生成、无多余依赖和无用实验模块混入发布配置；测试覆盖关键成功/失败路径，性能开销可解释；与 P4 实测行为等价。

### P6：最终安全审查、发布与维护

- PR 强制审查：输入白名单、固定 HTTPS Endpoint、TLS 信任边界、API Key 最小权限与撤销、日志脱敏、数据留存、错误码、流式解析/压缩、并发竞争、失败回退、自动构建一致性。
- GitHub Actions：lint/语法、单元测试、协议 fixture、故障注入、秘钥扫描/证书阻止、生成文件漂移、构建可重复性、最低版本兼容。修复红灯原因而非关闭检查。
- 真机验收必须再次覆盖“正常、模型失败、脚本未执行、断网/切换、连续提问、并发、Siri UI 确认”，保存脱敏截图和结果矩阵。
- 版本规则：若 P4 来源保证失败，只能保留 LAB；成功后才考虑 beta，不能只根据 CI 绿灯标成可用。
- 最终交付：一个可安装实验/正式模块（依验收结论）、清晰脚本、配置文档、回滚流程、测试报告和剩余风险清单。

## 4. 验收测试矩阵（必须有证据）

| 场景 | 预期答案来源 | 允许结果 | 不允许结果 |
|---|---|---|---|
| 单次 Siri 文本问答 | DeepSeek | 原生界面呈现 DeepSeek 文本 | 千问文本或混合文本 |
| 连续 10 次不同问题（目标批次） | DeepSeek | 全部无串话、无错配 | 前一题答案、千问答案 |
| 两个并发/快速请求 | DeepSeek | 正确关联或明确拒绝 | 互换答案 |
| DeepSeek 401 / 429 / 5xx | 无回答 | 明确失败且不显示千问 | 回退千问 |
| DeepSeek 超时 / 网络断开 | 无回答 | 明确失败且不显示千问 | 回退千问 |
| 脚本异常或未触发 | 不可保证 | 必须识别为不满足发布条件 | 宣称稳定“仅 DeepSeek” |
| SSE 未知字段 / 分块变化 | 无回答 | 安全拒绝并记录错误码 | 残留千问片段 |
| 重启/锁屏/VPN 切换 | 需重新验证 | 标为支持或明确限制 | 未经测试宣称保证 |
| API Key 日志和文件扫描 | 不应出现 | 无真实敏感数据 | Key/CA/正文入库 |

测试数据只用虚构、可公开文本；真实用户隐私内容不进入 CI。测试次数是初始目标不是统计可靠性证明，必要时增加重复测试。

## 5. 安全与隐私威胁模型（新目标）

| 风险 | 严重程度 | 对策 |
|---|---|---|
| 千问可能获得原始问题 | 用户已接受的隐私取舍 | 首次启用前显式告知；不再声称零出站 |
| 最终答案混入千问文本 | **阻断发布** | 全路径来源校验、字段级替换、残留审计、真机故障注入 |
| 脚本未运行导致原生千问回退 | **阻断“必定 DeepSeek”承诺** | 故障测试；如宿主不可控则承认方案能力不足 |
| DeepSeek Key 泄漏或被滥用 | 高 | 不入仓/URL/日志，设备本地受限保存，撤销与额度控制 |
| MITM CA 被滥用 | 高 | 本机生成、仅目标主机、最小信任、停用与卸载流程 |
| SSE 注入/恶意字段/JSON 越界 | 高 | 结构化解析、长度/深度/事件数量限制、白名单型重写 |
| 请求错配、持久化隐私内容 | 高 | 随机短 token、TTL、内存优先、过期清除 |
| 上游结构变动导致绕过改写 | 高 | 未知结构 fail-closed、检测、版本锁定及再测试 |
| 性能成本与双上游 | 中 | API 调用去重、限并发/超时/额度、可配置关闭 |

**绝不把“DeepSeek API 已被调用”当作“最终 Siri 回答一定来自 DeepSeek”的证明。** 这是本项目与普通网络重写脚本最重要的验收区别。

## 6. 工作顺序、提交纪律与阻塞决策

执行顺序：P0 → **P1（最优先）** → P2 → P3 → **P4（发布硬门槛）** → **P5（必做结构重构）** → P6。

- 每一阶段记录：变更文件、决定、模拟测试结果、真机实际结果、已知阻塞、下一步。GitHub PR 和 docs 同步。
- 源码改动与生成文件放同一变更集，执行 npm run build、npm run check；不得通过删测试或关安全扫描使 CI 变绿。
- 新路线单独分支/PR，与旧 e4/transport 实验 PR 分开；main 在审查通过前保持历史安全默认配置。
- **P1 失败**：暂停 P2/P3，仅定位客户端响应替换是否可行；若无法安全接管 Siri UI，停止 Shadowrocket 路线，而不是偷换为快捷指令。
- **P4 失败**：功能即使演示成功也不能宣称“答案一定来自 DeepSeek”；保留实验标记，记录无法控制的系统级回退。
- **P5 失败**：撤销重构提交，保留已验证的正确功能；不得牺牲来源、密钥和故障边界换取更短代码。
- 用户真机操作按一次一项进行；代码开发、文档、CI 可由维护者直接处理。任何真实 API Key 或私密材料只在用户本地配置，不需要在聊天发送。
